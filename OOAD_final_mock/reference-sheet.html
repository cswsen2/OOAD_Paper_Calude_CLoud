  • static: belongs to the class, not to instances. One copy is shared by every object.
  • One public class per .java file, and the file name must match it.
  • Constructor: same name as the class and no return type, not even void. It runs automatically when an object is created. Default = no parameters; overloaded = takes parameters. this(...) calls another constructor. A method void Room() is just a method.
  • Overloading: same name, different parameters.
  • Encapsulation: group attributes and methods; keep data private and reach it through public methods (information hiding). Abstraction: keep only the essentials, relative to the viewer's perspective.
  • 4 pillars: abstraction, encapsulation, inheritance, polymorphism (different objects treated uniformly through one interface).
  • Class = blueprint (common noun); object = specific instance (proper noun).

  • Catch or specify: code that can throw a checked exception must catch it or declare it with throws. The compiler enforces this. Unchecked exceptions are exempt.
  • throw new X("msg") throws; throws X, Y declares (comma-separated).
  • Once a statement throws, the rest of the try is skipped. Control never returns to the try; it carries on after the try/catch.
  • Multiple catch: catches are inspected in order; the first match runs and the rest are skipped.
  • Multi-catch (Java 7): catch (IOException | SQLException e). The parameter is implicitly final and cannot be reassigned.
  • finally runs whether or not an exception is thrown or caught (use it for house-keeping).
  • Nested try: if the inner try has no match, the parent try's catches are inspected.
  • Uncaught: the default handler prints the stack trace and terminates the program.
  • Compile-time errors: no .class file is produced. Run-time errors: it compiles, then fails while running.
class MyEx extends Exception {
    MyEx(String m) { super(m); }
}   // checked: catch or declare
catch (MyEx e) { e.getMessage(); }

  • Create: extends Thread, or implements Runnable + new Thread(r). Override run().
  • start() creates a new thread, and the JVM calls run(). Calling run() directly is an ordinary call on the current thread.
  • join(): the caller waits until that thread dies. yield(): Running → Ready (gives same-priority threads a turn).
  • sleep(ms) keeps the lock and throws InterruptedException.
  • wait() releases the lock, moves to Waiting, and throws InterruptedException. notify() wakes one waiting thread (→ Ready). notifyAll() wakes all threads waiting on that object. They must be called while holding the lock, otherwise IllegalMonitorStateException.
  • Priority: min 1, normal 5, max 10. Daemon threads die when the JVM exits (when only daemons are left).
  • Threads share code, data (static + heap) and open files; each has its own ID, registers and stack.
  • Race condition: the result depends on scheduling when threads modify shared data without synchronization.
synchronized void m() { … }
    // locks this object
synchronized (shared) { … }
    // locks shared
synchronized (new Object()) { … }
    // WRONG: new lock each call

// guarded wait: re-check on waking
synchronized void take()
        throws InterruptedException {
    while (!ready) { wait(); }
    …   // condition holds here
}
synchronized void give() {
    ready = true;
    notifyAll();
}

Generics

  • "Parameterized types": type-safe, no casts needed, checked at compile time. Conventions: T type, E element, K key, V value, N number.
  • No primitives: use wrappers (int→Integer, char→Character, double→Double…). Autoboxing: primitive→object; unboxing: object→primitive (since J2SE 5.0).
class Box<T> {
    T obj;
    void add(T v) { obj = v; }
    T get() { return obj; }
}
class Pair<T, V> { … }  // 2 params
static <E> void show(E[] a) { … }
class Stats<T extends Number> {
  … nums[i].doubleValue() … }
<T extends Cls & Intf> // class 1st
void draw(List<? extends Shape> l)

Limitations: no new T(); no static member using the class's T (static generic methods are OK); no arrays of a type parameter; no generic exception classes (cannot extend Throwable). Stats<String> fails: String is not a Number.

OO analysis: noun/verb & CRC

  • Nouns → candidate classes (common noun = class, proper noun = object). Verbs → candidate methods. Unclear owner? Use CRC cards.
  • 5 rejection rules: Redundant (same concept, two names) · Meta-language (words about the text or language itself) · Event or Operation (something that happens) · Outside scope of system · An attribute (a property of another class).
  • CRC card: class name (top) | Responsibilities (left) | Collaborators (right). Responsibilities come from verbs and are not methods (one may need several methods). A collaborator is a class needed to meet a responsibility; a card can have none.
  • An actor becomes an entity class only if its data matters to the domain. Analysis classes: «entity» (domain data), «boundary» (one per actor: forms, reports), «control» (one per complex use case).

Design patterns

Creational: Singleton, Factory Method, Abstract Factory. Behavioral (lecture's grouping): Command, Strategy, Bridge*, Template Method. *GoF lists Bridge as structural.

Singleton: one instance + global access point

private static S unique;
private S() { }
// lazy: single-threaded only
static S getInstance() {
  if (unique == null)
      unique = new S();
  return unique; }
// safe but costly:
static synchronized S getInstance()
// eager, created at class load:
private static S unique = new S();
// double-checked locking:
private volatile static S unique;
  if (unique == null)
    synchronized (S.class) {
      if (unique == null)
        unique = new S(); }
// simplest:
enum S { UNIQUE_INSTANCE; }

It needs a private constructor, a private static instance and a static getInstance(). Pitfalls: several class loaders can each make one; it is tightly coupled; it has two responsibilities.

Factory Method vs Abstract Factory

  • Factory Method: relies on inheritance; subclasses decide which product to create (abstract createX()). Steps: interface → concrete classes → Factory → client passes a type.
  • Abstract Factory: an interface for creating families of related objects without naming concrete classes. It relies on object composition. Each concrete factory produces one consistent family. A FactoryProducer returns the right factory.

Notes' example: PizzaIngredientFactory declares createDough(), createSauce(), …; NYPizzaIngredientFactory returns ThinCrustDough, MarinaraSauce…, and ChicagoPizzaIngredientFactory returns ThickCrustDough, PlumTomatoSauce…, one whole regional family each.

Command: decouples requester from performer

RoleJob
Clientcreates ConcreteCommands and sets each one's Receiver
Commandinterface: execute() (+ undo())
ConcreteCommandbinds an action to a Receiver
Invokerholds commands and calls execute()
Receiverknows how to do the actual work
  • NoCommand (null object): its execute(){} does nothing, so slots need no null checks.
  • undo() mirrors execute() (on ↔ off). History in a Stack: pop() the last command, then undo it.
  • MacroCommand: holds an array or list of commands; execute runs them in order, and undo runs them in REVERSE (last one first).

Bridge · Strategy · Template Method

  • Bridge: vary the abstraction and the implementation independently by placing them in separate hierarchies. The abstraction holds a reference to the implementor interface. Adding an implementor changes no abstraction class.
  • Strategy: a family of interchangeable behaviours, swapped at run time (setFlyBehaviour(...)).
  • Template Method: a final method fixes the steps of an algorithm; subclasses implement the abstract steps.

Use case diagrams

  • Actor: anything that interacts with the system (a person or an external system). Black box, always outside the boundary. Drawn as a stick figure or an «actor» box.
  • Use case = an oval inside the system boundary: a job done for an actor, with pass/fail criteria. A communication line joins actor and use case.
  • «include»: the base always includes it (purchase → process payment). «extend»: optional, under a condition (seasonal discount → purchase).
  • Actor generalization: the specialised actor can do everything the general one can, plus more (Administrator → User).
  • Use case scenario: a step-by-step text of one path through a use case.

Requirements Engineering

  • Goal (high-level objective) → Feature (related requirements that satisfy a goal) → Requirement (how the system achieves it).
  • Levels: user (natural language, ConOps, user stories) → system (precise, SRS, use cases) → design specification.
  • FR: services the system provides and how it reacts to inputs. FRs may state what the system should NOT do.
  • NFR: security, reliability, maintainability, performance, usability, testability, interoperability, plus constraints (design, implementation, financial, resource). Domain requirements come from the domain.
  • Process: Elicitation → Analysis & reconciliation → Representation/modeling → Verification & validation ("Am I building the right product?") → Management (change, traceability, scope creep).
  • shall = must be met; should = desirable, dropped first. User story: As a [user], I want [goal] so that [benefit].
  • Raw requirements may be contradictory, inconsistent, incomplete, vague or wrong, or depend on each other. Representations can be informal, formal or semiformal.
